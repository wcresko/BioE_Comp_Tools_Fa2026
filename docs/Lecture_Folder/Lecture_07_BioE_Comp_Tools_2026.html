Literate programming and reproducible science

Your paper and your analysis drift apart

  • The classic workflow:
    • analyze over here (scripts, console)
    • write over there (Word)
    • hand-carry numbers and figures between them
  • Every revision re-opens the gap:
    • figure version five in a version-three draft
    • a mean in the text the code no longer produces
    • methods that describe last month’s analysis
  • Scientific bugs are usually silent - nothing crashes when the pasted number is stale
  • An analysis you cannot regenerate is one you cannot defend - to reviewers, collaborators, or yourself in six months

Literate programming: the document is the analysis

“Instead of imagining that our main task is to instruct a computer what to do, let us concentrate rather on explaining to human beings what we want a computer to do.” - Donald Knuth, Literate Programming (1984)

  • One plain-text document holds the prose, the code, and the results - rendering re-runs everything from data to figures
  • The numbers in your sentences are computed, not typed, so they can never disagree with your data
  • Your methods become self-documenting so inconsistencies between what you say and what you do become visible
  • We already do this - our lab notebook templates, the companion notebooks, this very slide deck and the course book are all Quarto

Reproducibility has a policy behind it: FAIR

  • Funders (including NIH and NSF) expect research outputs to be FAIR:
    • Findable - deposited somewhere with a persistent identifier, not “available upon request”
    • Accessible - retrievable by standard tools, no special software or permission maze
    • Interoperable - open, documented formats (tidy .tsv and .qmd)
    • Reusable - enough documentation and provenance that someone else can use it
  • Literate documents are FAIR practice
    • plain text any tool can read
    • methods that travel with the analysis
    • one source anyone can re-run

Quarto Markdown

Markdown: formatting in plain text

Markdown is a lightweight language: you type plain text with a few marks, and a renderer turns it into formatted output.

You type:

**bold** and *italic*,
`code`, ~~struck out~~,
x^2^ and H~2~O,
[a link](https://quarto.org)

You get:

bold and italic,

code, struck out,

x2 and H2O,

a link

Headers mark the document’s structure - one # per level:

# Chapter
## Section
### Subsection

Markdown: lists, quotes, tables, and images

You type:

3.  analyze

> Form follows function.

You get:

  • stickleback
  • zebrafish
    • AB strain
  1. collect
  2. measure
  3. analyze

Quarto Markdown

  • Quarto extends Markdown into a scientific publishing system.

  • A .qmd file is Markdown plus three ingredients:

  1. A YAML header - document settings and metadata at the top
  2. Executable code chunks - R or Python that runs when the document renders
  3. Scholarly machinery - callouts, cross-references, LaTeX math, and citations

  • One .qmd source renders to HTML, PDF, Word, slides, websites, and books

  • This slide deck, the course site, and the course book are all Quarto.

Ingredient 1: the YAML header

---
title: "Genotype effects on gut gene expression"
author: "Your Name"
date: today
format: html
---
  • The --- fences mark it off at the very top
  • Inside the YAML header is key: value pairs
  • It controls the whole document: format:
    • picks the output (html, pdf, docx, revealjs, …)
  • Options for a format nest beneath it, and execute:
    • sets defaults for every code chunk:
format:
  html:
    toc: true          # table of contents
execute:
  echo: false          # hide code everywhere, unless a chunk overrides

Ingredient 2: Markdown prose between the chunks

## Methods

We measured 600 genes in 80 fish across
**2 genotypes x 2 microbiota treatments**.

```{r}
counts <- read_tsv("data/Stickle_RNAseq.tsv")
```

## Results

The counts were *overdispersed*, so we...
  • Everything from the last two slides works unchanged - headings, emphasis, lists, images
  • The document reads as a narrative with the analysis embedded at the right moments
  • This is literate programming
  • Headings organize the output and your thinking: Methods, Results, etc….

Ingredient 3: executable code chunks

  • R
  • Python
```{r}
#| label: my-first-chunk

x <- 5
print(x^2)
```
```{python}
#| label: my-first-chunk-py

x = 5
print(x**2)
```
  • Three back ticks fence a chunk
    • {r} runs it through knitr
    • {python} through Jupyter
  • Everything else about the chunk - options, labels, captions - is identical in both languages
  • Mixing R and Python in one file works too (via the R package reticulate) - details in Ch. 16

Chunk options: the hash-pipe #|

Options go inside the chunk, one per line - identical in every language:

```{r}
#| label: fig-stiffness
#| echo: false
#| fig-cap: "Stiffness by hydrogel concentration"
boxplot(compression ~ hydrogel_concentration, data = mydata)
```
Option Effect
echo: false Run the code, hide the code (manuscripts!)
eval: false Show the code, don’t run it
include: false Run it, show nothing (setup chunks)
fig-cap: Figure caption
label: fig-... Makes the figure numbered and referenceable

Tip

  • Set document-wide defaults in the YAML under execute:

  • Override chunk by chunk only where needed.

Inline code so sentences don’t go stale

```{r}
#| include: false
stickle <- read_tsv("data/Stickle_RNAseq.tsv")
```

We measured `r ncol(stickle) - 3` genes in
`r nrow(stickle)` fish (@fig-gene1).
  • Renders as:

    • “We measured 600 genes in 80 fish (Figure 1).”

  • Re-run with more fish next month, or add a figure
    • the sentence updates itself
    • the figures are re-numbered automatically
  • This is a big practical win of literate programming

Cross-references: label it once, @ it anywhere

Label a figure, table, equation, or section; reference it with @; Quarto numbers everything, and renumbers on every render:

Type Label Reference
Figure #| label: fig-name or {#fig-name} @fig-name
Table #| label: tbl-name or {#tbl-name} @tbl-name
Equation $$ ... $$ {#eq-name} @eq-name
Section ## Heading {#sec-name} @sec-name

The render pipeline (@fig-pipeline) runs your code every time.

Mathematics with LaTeX

Inline math: a single pair of $

LaTeX notation dropped between $ signs flows with the sentence:

You type You get
$\sigma = E\varepsilon$ \(\sigma = E\varepsilon\)
$\bar{x} \pm 1.96\, s/\sqrt{n}$ \(\bar{x} \pm 1.96\, s/\sqrt{n}\)
$\mu = 2.5\ \mathrm{kPa}$ \(\mu = 2.5\ \mathrm{kPa}\)
$H_0\!: \beta_1 = 0$ \(H_0\!: \beta_1 = 0\)
  • Subscripts with _, superscripts with ^, Greek letters by name (\sigma, \mu, \beta)
  • Works identically in HTML, PDF, Word, and slides

Display math: a double pair of $$

A $$ pair puts the expression on its own centered line:

$$Pr(Y=r) = \frac{e^{-\mu}\mu^r}{r!}$$

\[Pr(Y=r) = \frac{e^{-\mu}\mu^r}{r!}\]

$$f(x) = \frac{1}{\sigma\sqrt{2\pi}}
         \, e^{-\frac{(x-\mu)^2}{2\sigma^2}}$$

\[f(x) = \frac{1}{\sigma\sqrt{2\pi}} \, e^{-\frac{(x-\mu)^2}{2\sigma^2}}\]

$$\iint xy^2 \, dx \, dy = \frac{1}{6}x^2y^3$$

\[\iint xy^2 \, dx \, dy = \frac{1}{6}x^2y^3\]

Numbered equations are cross-references too

You type (the {#eq-...} label sits on the same line as the closing $$):

$$
\mathrm{SE} = \frac{s}{\sqrt{n}}
$${#eq-se}

The standard error (@eq-se) shrinks with sample size.

You get:

\[ \mathrm{SE} = \frac{s}{\sqrt{n}} \tag{1}\]

Citations

The reference database: a .bib file

BibTeX is a plain-text database - one entry per source, each with a citation key:

@article{knuth1984literate,
  author  = {Knuth, Donald E.},
  title   = {Literate Programming},
  journal = {The Computer Journal},
  year    = {1984}
}

Wire it up in the YAML header:

---
bibliography: references.bib
csl: nature.csl        # optional: any journal's citation style
---
  • Zotero exports BibTeX directly
  • Google Scholar’s “Cite” button offers an entry for any paper
  • Keep one .bib per project and let it grow
  • Swap the .csl file and every citation re-styles itself for a different journal

Citing with @key - and what it renders

You type:

Knuth introduced literate programming [@knuth1984literate].
@knuth1984literate argued that programs are written for people.
Research outputs should be FAIR [@wilkinson2016fair; @knuth1984literate].

You get (these are real citations - this deck has its own .bib file):

Knuth introduced literate programming (Knuth 1984). Knuth (1984) argued that programs are written for people. Research outputs should be FAIR (Wilkinson et al. 2016; Knuth 1984).

And Quarto builds the reference list for free, wherever you put a #refs div:

>

Knuth, Donald E. 1984. “Literate Programming.” The Computer Journal 27 (2): 97–111. https://doi.org/10.1093/comjnl/27.2.97.

Rendering: one source, many outputs

What happens when you press render

Figure 1: The render pipeline: Quarto runs the code (knitr for R, Jupyter for Python), weaves the results into the Markdown, and hands the whole thing to Pandoc to produce the output format.

  • The code runs every time, so figures, tables, and inline numbers can never drift from the data
  • This figure is @fig-pipeline - the cross-reference you clicked three sections ago

Rendering commands

quarto render report.qmd              # the format named in the YAML
quarto render report.qmd --to pdf     # override: PDF (needs TinyTeX, installed once)
quarto render report.qmd --to docx    # override: Word
quarto preview report.qmd             # live preview - re-renders every time you save
quarto render                         # render a whole project or website
  • In Positron:
    • the Preview button, or Cmd/Ctrl + Shift + K
    • Or use the quarto preview and quarto render commands in the terminal
  • quarto preview is the one to use while writing
    • it opens the document beside your editor
    • refreshes on every save
  • PDF goes through LaTeX - install once with quarto install tinytex, then forget it’s there
  • Emailing a report?
    • Set embed-resources: true under format: html:
    • images, CSS, and JS are bundled into one self-contained .html file that travels on its own

One source, several formats

List several formats in the YAML and render them all at once:

format:
  html: default
  pdf: default
  docx: default

AI-assisted coding

“Vibe coding” and why it can fail in science

  • A large language model (LLM) predicts the most plausible next text - including code
  • Vibe coding = describe, accept, run, paste the error, repeat - without reading the code
  • Fun for a weekend project; a problem for science:
    • you have to defend every result
    • scientific bugs are usually silent (wrong number, no crash)
    • you stop learning
  • Here’s a different approach:
    • keep the speed, drop the blindness
    • the assistant writes, you read,
    • a tiny test decides

The loop

  1. Describe the goal precisely - language, versions, sample input, expected output
  2. Get code
  3. READ it - every line; look up anything you don’t recognize
  4. Run it on a tiny test you can check by hand
  5. Check the result against something you already know
  6. Iterate - paste the exact error or wrong output, say what you expected

Important

Steps 3 and 5 are the ones people skip. Don’t.

Where LLMs fail - the short list

  • Hallucinated functions, packages, and arguments - delivered with total confidence
  • Outdated APIs - last year’s function names in this year’s package
  • Subtly wrong statistics - sd(x) / n instead of sd(x) / sqrt(n); mean() when you asked for median()
  • Silently changing your data - dropping every row with an NA, re-sorting and breaking an alignment

  • The failures have the same root cause

  • The model predicts text, it does not reason about your data

  • The fix: read the code, test on an input where you know the answer.

  • Ch. 18 has worked examples of each failure and a review checklist.

Data rules and the course policy

Never paste into an unsupported AI tool:

  • Unpublished data or results · human-subjects data / PHI · credentials
  • UO data classes:
    • green (published data, your code)
    • amber (unpublished research, FERPA)
    • red (HIPAA).
  • Unsupported tools: green only; Microsoft Copilot Chat with your UO login is covered by UO’s agreement - see UO’s AI Service Offerings
